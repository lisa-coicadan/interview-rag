# Interview RAG

Personal interview-prep assistant built on my own documents (CV, professional experience, company-specific prep notes, technical notes). Rather than a generic chatbot, this project retrieves the relevant passages from my document base before generating an answer — a RAG (*Retrieval-Augmented Generation*) pipeline built by hand, with no abstraction framework (no LangChain), to understand every step of the mechanism.

Personal, learning-focused project: the main goal was to get hands-on, practical experience with how a RAG system works end-to-end and with using an LLM API key in a real application — not just to end up with a polished tool.

## Architecture

```text
Documents (documents/)
      ↓
Chunking (splitting into overlapping pieces)
      ↓
Embeddings (OpenAI text-embedding-3-small)
      ↓
ChromaDB (vector database, persisted to disk)
      ↓
User question
      ↓
Question embedding
      ↓
Similarity search in ChromaDB
      ↓
Most relevant chunks
      ↓
Augmented prompt (context + history + question)
      ↓
OpenAI API (gpt-4o-mini)
      ↓
Answer
```

## Stack

- Python
- OpenAI API (`responses.create` for generation, `embeddings.create` for embeddings)
- ChromaDB (local vector database, persisted in `chroma_db/`)
- Streamlit (web interface)
- `python-dotenv` (environment variables)

## Code structure

```text
utils.py       → OpenAI client, ChromaDB connection, get_embedding(), chunk_text()
ingest.py      → walks documents/, chunks and vectorizes each file, feeds ChromaDB
app.py         → Streamlit interface (one conversation per company, history, RAG)
main.py        → terminal version of the search + answer pipeline, useful for quick tests
documents/     → my source documents (not versioned, see Privacy)
chroma_db/     → vector database generated by ingest.py (not versioned, regenerable)
```

## How the RAG works

1. **Ingestion** (`ingest.py`, rerun whenever documents change): each `.txt` file under `documents/` is split into chunks along its section headers (falling back to a fixed size for long sections), each chunk is turned into a vector (embedding), and stored in ChromaDB with metadata derived from its file path (`company`, `category`, `type`, `source_file`). Re-ingesting a file first deletes its previous chunks (matched by `source_file`), so a shrunk file doesn't leave orphaned chunks behind.
2. **Query** (`app.py` / `main.py`, on every question): the question itself is turned into an embedding, compared against the stored vectors (cosine similarity), and the closest chunks are retrieved.
3. **Generation**: the retrieved chunks are inserted into a prompt along with the question, sent to the OpenAI API. The model is explicitly instructed to answer only from the provided context.

Important point: RAG does not train the model. No personal data is remembered by OpenAI from one request to the next — the relevant context is looked up and re-injected on every single call.

## Technical choices

- **No LangChain**: the pipeline (chunking, embeddings, search, augmented prompt) is written by hand to understand each mechanism, rather than depending on an abstraction layer.
- **Metadata derived from file path**: the structure of `documents/` (`entreprises/<company>/`, `experiences/`, `technique/`) is used directly to build ChromaDB metadata, with no manual per-document configuration.
- **Conversation history handled manually**: `client.responses.create()` is stateless — history (stored in `st.session_state`, one entry per conversation) is rebuilt and re-injected into the prompt on every question, not a native memory of the model. A "Restart this conversation" button clears the active conversation's history without touching the others.
- **Metadata filtering at search time**: search is restricted to the active conversation's company (`where={"company": ...}`), or to `category: "technique"` for "Technical learning"; no restriction for "General". Initially left out (to let the model cross-reference experiences across companies, e.g. surfacing a past professional experience while discussing a different company), then adopted after observing in practice that structurally similar documents from different companies (same section headings, same recruitment-process outline) could compete in retrieval and produce answers that mixed up two different companies.
- **`n_results=5`** (instead of 3): a relevant chunk (a "Responsibilities" section) wasn't always in the top 3. This isn't a dial to simply max out: more chunks improves recall but dilutes the context and increases the risk of conflation (see Known limitations).

## Known limitations

A qualitative evaluation on real test questions surfaced several concrete limitations:

- **Retrieval errors**: for some questions, the most relevant chunk isn't always ranked highest, or can be missing from the top results entirely if its wording differs from the question.
- **Conflation**: the model can occasionally blend information from two different chunks into one plausible-sounding but factually incorrect answer (attributing a fact to the wrong experience). This is a structural limitation of RAG to watch for, not an isolated bug — and a risk that increases with `n_results`, not decreases.
- **No notion of document freshness**: the pipeline treats every chunk as equally valid, with no awareness that one document might supersede another. For example, prep notes written *before* an interview and the actual transcript written *after* carry the exact same status for ChromaDB — if the former is closer in distance to the question, it can outrank the latter, producing an answer that ignores what actually happened.
- **Perceived wording quality lower than ChatGPT**: even when the content is correct, answers can feel less fluent than a general-purpose assistant — likely the cost of a strict prompt ("answer only from the context") versus a model otherwise optimized for open conversation. Unexplored angle: tune the system prompt for a better fidelity/fluency balance.
- **ChromaDB index fragility**: after many successive adds/deletes/upserts, a query using `where` eventually raised an internal error (`Error finding id`). Since `chroma_db/` is fully regenerable from `documents/` via `ingest.py`, the fix was to rebuild it from scratch rather than diagnose the index's internal state.

These limitations illustrate that a RAG system isn't judged as "works / doesn't work" — it needs to be assessed along several independent axes: retrieval quality, generation faithfulness, absence of hallucination, and freshness of the source data.

## Privacy

`documents/` (my personal documents) and `chroma_db/` (derived data) are not versioned — see `.gitignore`. This repository contains only the pipeline code, not my data.

## Setup

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Create a `.env` file at the project root with:

```text
OPENAI_API_KEY=your_key_here
```

Ingest documents (bring your own `documents/` folder):

```bash
python3 ingest.py
```

Run the interface:

```bash
streamlit run app.py
```

## Possible next steps (V2)

- Handle document freshness (e.g. a metadata field distinguishing prep notes from an actual transcript, or a date, to prioritize the most up-to-date information).
- Reduce `chunk_size` for topically tighter chunks, as an alternative to raising `n_results`.
- Persistent conversation memory (beyond the current session).
- Agentic architecture: an orchestrator dynamically deciding which source to query (personal RAG, company RAG, web search) rather than a fixed, deterministic pipeline.
